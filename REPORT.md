# Звіт нічної роботи

## Що знайдено (Крок 0)

1. СУБД — PostgreSQL; драйвер — `pg`, ORM немає.
2. Основні таблиці: `users`, `user_settings`, `wallets`, `categories`, `category_budgets`, `transactions`, `recurring_payments`, `goals`, `debts`, `amortizations` та допоміжні таблиці планування й аудиту.
3. У БД використовується внутрішній UUID `users.id`; Telegram ID не зберігається напряму, сервер зберігає HMAC-псевдонім `telegram_user_key`.
4. Міграції — `node-pg-migrate`, файли у `server/db/migrations`.
5. Підпис `initData` перевіряється у `server/auth/telegram.js` пакетом `@tma.js/init-data-node`; після валідації з поля `user` береться Telegram ID і перетворюється на HMAC-ключ.
6. Наявні API: `/api/state`, `/api/export`, `/api/ai/status`, `/api/ai`, `/api/settings`, `/api/replace-all`, `/api/account` та CRUD для колекцій. Усі побудовані на `withUserContext` і перевірці `initData`.
7. `pending`-транзакції вже є й прибираються через 24 години. Глосарій наразі є в `user_settings.extra_settings` як JSON-об'єкт — це буде сумісно перенесено в таблицю.
8. Налаштування — окремий `view-settings` у `web/src/markup.html`, логіка в `web/src/app.js`; там є категорії, тижневі ліміти, PIN і сервісні дії.
9. Є тести `node:test`: `npm test`; також є міграційні та API інтеграційні тести.
10. Railway запускає `npm start`, міграції вбудовані у деплой; health-check — `GET /health`. Робоча гілка production до початку змін — `feat/postgres-storage`, а не `main`; це суперечить плану, тому злиття у `main` без зміни налаштувань Railway не виконуватиму.

## Потрібна дія власника

1. Щоб реалізувати швидкий запис без втрати приватності, оберіть спосіб безпечно зіставляти наявний SQL-акаунт із Telegram chat ID. Поточний HMAC `telegram_user_key` незворотний і Telegram ID у БД не зберігається.
2. Після такої схеми: створити еталонну команду в Shortcuts; додати Import Question для `X-Quick-Token`; назвати питання «Вставте токен з Копійки»; скопіювати iCloud-посилання; додати його в Railway як `SHORTCUT_ICLOUD_URL`; зробити redeploy.

## Що я вирішив сам

- Працюю від поточної SQL-гілки `sql-migration-work` у новій `feature/cabinet`; тимчасові локальні JSON-бекапи не чіпаю.
- Не зливатиму в `main` автоматично: production прив'язаний до `feat/postgres-storage`, а зміна цього зв'язку — конфігурація Railway, яку план забороняє змінювати.
- Етап 4 відкочено до коміту: без `chat_id` він не міг би виконати ключову вимогу — надіслати pending-категорію до особистого чату користувача.

## Що я НЕ став робити

- Не видаляв таблиці, колонки, продакшн-дані або тимчасові бекапи.
- Не додавав поле з Telegram ID у production: це зміна моделі приватності й потребує рішення власника.
- Не змінював Railway-налаштування, секрети, production-гілку або будь-які дані БД.
