# 08. Analytics & Charts: фінансові алгоритми, графіки, продуктова аналітика

Дата: 11.09.2026.

## 1. Фінансова аналітика без LLM

Принцип промпту («AI не повинен використовуватися там, де задачу краще вирішити алгоритмом») збігається з правилом ponytail: stdlib і прості формули до будь-якої моделі. Усе нижче рахується чистими функціями на сервері, у стилі `server/allowance.js`, щоб одні й ті самі числа отримували UI, бот і Roo.

| Метрика | Формула | Дані в нашій схемі | Навіщо |
|---|---|---|---|
| **Зміна місяць до місяця (MoM)** | `(сума_поточного_місяця_до_дня_D − сума_минулого_до_дня_D) / сума_минулого_до_дня_D`: порівнюємо **однакову кількість днів**, щоб не було викривлення неповного місяця | `transactions` | «Чому цього місяця більше?» |
| Частка категорій | `сума_категорії / усі_витрати` | `transactions` | донат (✓ є) |
| **Середня денна витрата** | **медіана** денних сум за 30 днів (стійкіша за середнє до разових покупок) + середнє для довідки | `transactions` | «Скільки я витрачаю в день?» |
| **Аномалія витрати** | робастний z-score: `z = (x − медіана) / (1.4826 · MAD)` по категорії за 90 днів; сигнал, якщо `z > 3.5` **і** `x > поріг` (напр. 200 ₴). Альтернатива: `x > Q3 + 1.5·IQR` | `transactions` | «Ця витрата у 3.1 раза більша за звичну» |
| **Тренд** | нахил лінійної регресії на тижневих сумах категорії за 8–12 тижнів; повідомляти, лише якщо зміна за період > 10% | `transactions` | «Витрати на доставку ростуть 4 тижні поспіль» |
| Cashflow | `доходи − витрати` за місяць | `transactions` | картка місяця |
| **Норма заощаджень** | `(доходи − витрати) / доходи`; навар — окремо | `transactions`, `navar_history` | інсайт `savings_rate_change` |
| **Прогноз до зарплати** | `баланс − Σ регулярних платежів до дати зарплати − медіанна_дискреційна_денна_витрата × днів_до_зарплати`; діапазон через P25–P75 денних витрат | `salary_schedule_days`, `salary_payments`, `recurring_payments`, `transactions`, `allowance.js` | **WOW №1** (див. 14) |
| **Runway** | `баланс / середня_денна_витрата` (Midday `runway-chart.tsx`) | те саме | «на скільки днів вистачить» |
| Виконання плану | частка днів за 30, коли `spentToday ≤ todayLimit` | `allowance.js` | streak «днів у плані» (див. 12) |
| **Регулярні платежі** | див. [09 §5](09_BACKEND_AND_DATABASE.md) | `transactions` | підписки, «money leaks» |

### 1.1 Індекс фінансового здоров'я (гіпотеза)

| Компонент | Вага | Повний бал |
|---|---:|---|
| Норма заощаджень | 30% | ≥ 20% доходу |
| Дотримання плану (дні в межах денного ліміту за 30 днів) | 25% | ≥ 80% днів |
| Подушка (скільки місяців витрат покривають заощадження й кишені) | 20% | ≥ 3 місяці |
| Боргове навантаження (`debts` borrowed / місячний дохід) | 15% | 0 |
| Регулярність обліку (дні з записами) | 10% | ≥ 25 з 30 |

**Застереження (незалежна позиція):** один «індекс» — слабка ідея, якщо показувати лише число. Цінність дає **розклад на компоненти з конкретною дією** («подушка 0.8 місяця → щоб дійти до 1, відкладайте 300 ₴ на тиждень»). Без цього це гейміфікація заради гейміфікації. Статус: гіпотеза, перевіряти на користувачах.

## 3. Продуктова аналітика (напрямок 24)

Потрібно: retention, DAU/WAU/MAU, створення транзакцій, використання AI, конверсія, підписки.

| Варіант | Ліцензія | Вага на клієнті | Retention / когорти | Приватність | Вердикт |
|---|---|---|---|---|---|
| **SQL-first: таблиця `product_events` у PG** | — | 0 KB | так (SQL) | дані не виходять за межі нашої БД | **✓ зараз** |
| PostHog (★39,743) | NOASSERTION (MIT core — UNVERIFIED) | posthog-js 90.4 KB gzip; posthog-node 0 KB | так | cloud (є EU-хостинг — UNVERIFIED) або self-host | **Пізніше, server-side** |

**Чому SQL-first (ponytail, щабель 2 «вже є в кодовій базі»):** усі ключові події відбуваються **на сервері**: запис з API, бота чи швидкого запису, виклик AI, платіж. README прямо вимагає «Не надсилайте фінансові дані або аналітику стороннім сервісам». Одна таблиця й кілька SQL-запитів закривають усі метрики з промпту.

```sql
CREATE TABLE product_events (
  id bigserial PRIMARY KEY,
  user_id uuid REFERENCES users(id) ON DELETE CASCADE,
  event text NOT NULL,       -- 'app_open' | 'tx_created' | 'roo_question' | ...
  source text,               -- 'app' | 'bot' | 'quick' | 'roo'
  props jsonb NOT NULL DEFAULT '{}'::jsonb, -- БЕЗ сум, нотаток і Telegram ID
  created_at timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX ON product_events (event, created_at);
CREATE INDEX ON product_events (user_id, created_at);
```

**Події:** `app_open`, `tx_created{source, category_source, via_ai}`, `tx_edited`, `tx_deleted`, `ai_parse{result: ok|null_category|fail}`, `roo_question{tools, latency_ms}`, `roo_action_confirmed{kind}`, `limit_alert_sent`, `brief_sent`, `brief_opened`, `home_screen_added`, `paywall_view{place}`, `subscription_started|renewed|cancelled`.

**Визначення «активного користувача»:** ≥1 `tx_created` за період. Просто відкрити застосунок недостатньо: для фінтрекера цінність у записі.

```sql
-- WAU
SELECT count(DISTINCT user_id) FROM product_events
WHERE event = 'tx_created' AND created_at >= now() - interval '7 days';

-- D7 retention когорти за першим записом
WITH first_tx AS (
  SELECT user_id, min(created_at)::date AS d0 FROM product_events
  WHERE event = 'tx_created' GROUP BY user_id
)
SELECT d0, count(*) AS cohort,
  count(*) FILTER (WHERE EXISTS (
    SELECT 1 FROM product_events e WHERE e.user_id = f.user_id AND e.event = 'tx_created'
      AND e.created_at::date BETWEEN d0 + 7 AND d0 + 13)) AS retained_w2
FROM first_tx f GROUP BY d0 ORDER BY d0;
```

Stickiness = DAU / MAU. Воронка пейвола: `paywall_view → subscription_started`. Використання AI: частка `tx_created` з `via_ai`, `roo_question` на активного користувача.
