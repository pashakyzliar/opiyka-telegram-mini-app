# 09. Backend & Database: БД, схема, фонові задачі, monobank, регулярні платежі

Дата: 11.09.2026.

## 1. Поточний стан (✓ з коду та README)

- **PostgreSQL** (Railway), драйвер `pg`, міграції `node-pg-migrate` (`server/db/migrations/001–006`). ORM немає, використовується репозиторний шар `server/repositories/account-repository.js`.
- **Гроші** — `NUMERIC(18,2)`, дати — `date`, мітки часу — `timestamptz`. `jsonb extra_data` зберігає сумісні невідомі поля.
- **Ізоляція:** HMAC-псевдонім Telegram ID (`telegram_user_key`), RLS-політики `*_isolation` на всіх таблицях, composite FK з `user_id`, advisory lock на запис.
- **API:** `node:http` без фреймворку (`server/app.js`): `/api/state` (повний стан), CRUD колекцій, `/api/roo/chat`, `/api/ai`, `/api/quick` (швидкий запис за токеном), `/api/export`, `/health`.
- **Клієнт** опитує `/api/state` кожні 45 с. Поки вкладка прихована, опитування зупиняється (`web/telegram-adapter.js:233`).

## 4. Фонові задачі та сповіщення

| Варіант | Сховище | Переживає рестарт | Дедуплікація | Для нас |
|---|---|---|---|---|
| `setInterval` у процесі | пам'ять | ні | ні | достатньо для нечастих задач, поки одна репліка |
| node-cron (★8,948) | пам'ять | ні | ні | те саме, лише зручніший синтаксис |
| **pg-boss** (★3,944, MIT, реліз 12.31.0 від 10.09.2026) | **PostgreSQL** | так | singleton-ключі, cron, повтори, `throttle` | **✓ коли запуститься перша регулярна продуктова функція** (ранковий бриф / тижневий звіт) |
| graphile-worker (★2,385) | PostgreSQL (LISTEN/NOTIFY) | так | так | альтернатива pg-boss |
| BullMQ (★9,390) | **Redis** | так | так | IGNORE: нова інфраструктура |

**Чому pg-boss, а не `setInterval`:** при деплої на Railway стара й нова репліки деякий час живуть разом, і `setInterval` у кожній відправить **той самий** бриф двічі. Singleton-задачі pg-boss у спільній PG це виключають. Нової інфраструктури не треба.

| Сповіщення | Тригер | Потрібен планувальник? |
|---|---|---|
| Ліміт категорії 80% / 100% | після запису (подія) | ні: у відповіді бота вже є блок денного плану (`formatAllowanceBlock`, `bot-ai.js:260`), розширити |
| Незвична витрата | після запису | ні |
| Найближчий регулярний платіж | щодня | так |
| Ранковий бриф | щодня за **локальним** часом користувача | так + `timezone` |
| Тижневий / місячний звіт | cron | так |

Ліміти розсилки Bot API (близько 30 повідомлень на секунду сумарно) — **UNVERIFIED** на поточну дату. Закласти `throttle` у pg-boss.

## 5. Автовиявлення регулярних платежів

Зараз регулярні платежі в «Копійці» **лише ручні** (`recurring_payments`: назва, сума, категорія, день місяця).

### 5.1 Алгоритм (синтез трьох відкритих реалізацій)

| Крок | Параметр | Джерело |
|---|---|---|
| 1. Групування | нормалізована нотатка (`normalizeWord`), а для банківських операцій — мерчант / `counterName` + категорія | GiGurra `detector.go` (група за payee) |
| 2. Частота | тип за медіаною інтервалів: weekly (7±2), biweekly (14±2), monthly (28–31, **рівно 1 на календарний місяць**) | Actual `find-schedules.ts` (weekly / every2weeks / monthly, дата ±2 дні), GiGurra `IsMonthlyPattern` |
| 3. Сума | кластер у межах **±7.5%** від ковзного середнього (фіксовані підписки); для змінних (комуналка) — окремий тип `variable` з допуском 35% | Sure `identifier.rb` (`DEFAULT_TOLERANCE_PCT = 7.5`), GiGurra (35% між сусідніми) |
| 4. Поріг | **2 входження → запропонувати**, **3 → вважати впевненим** | Sure `identifier.rb`: «Two consistent occurrences are enough to OFFER a candidate (the automatic pipeline keeps requiring three)» |
| 5. Дедуплікація | не пропонувати те, що вже є серед ручних; **відхилене користувачем пам'ятати** (надгробок) | Sure: «detection can never recreate a bill the user already declared by hand or dismissed» |
| 6. Статус | active / stopped (пропущено ≥2 періоди) | GiGurra `DetermineStatus` |
| 7. Зміна ціни | остання сума > середньої на X% → інсайт «подорожчало» | Sure `price_change_detector.rb` |
| 8. Дохід | за **джерелом**, не за сумою: зарплата буває змінною | Sure `income_source_candidates` |

**Реалізація:** `server/recurring-detect.js` — чиста функція `(transactions, existingRecurring, dismissed) → suggestions[]`. Запускати після кожного запису (дешево: дані вже в пам'яті) або щоночі через pg-boss. Результат пишеться в `recurring_suggestions (user_id, key, kind, cadence, avg_amount, last_date, next_date, status: suggested|dismissed|accepted)`. UI — картка в «Кишенях»: «Схоже на регулярний платіж: Netflix 349 ₴ ~5-го числа. Додати?». Той самий список отримує Roo (`get_recurring`).

**Обмеження ручного введення:** користувачі пишуть «нетфлікс», «netflix», «підписка». Детектор на нотатках працює гірше, ніж на банківських мерчантах. Звідси стратегічна цінність monobank-імпорту (§6).

## 6. monobank: автоімпорт для українського продукту

Факти з [документації monobank open API v250818](https://api.monobank.ua/docs/index.html), прочитано 11.09.2026:

| Що | Деталі |
|---|---|
| Авторизація | персональний `X-Token` з кабінету api.monobank.ua |
| `GET /personal/client-info` | рахунки (баланс, валюта, IBAN, maskedPan), **банки** (`jars`: title, balance, goal). Не частіше ніж раз на 60 с |
| `GET /personal/statement/{account}/{from}/{to}` | до **31 доби + 1 години** за запит, раз на 60 с. Поля: `id`, `time`, `description`, **`mcc`**, `originalMcc`, `hold`, `amount` (у копійках), `operationAmount`, `currencyCode`, `commissionRate`, `cashbackAmount`, `balance`, `comment`, `receiptId`, `counterName`, `counterIban` |
| **Webhook** | `POST {type:"StatementItem", data:{account, statementItem}}`. Якщо відповіді немає 5 с, повтор через 60 та 600 с; після третьої невдачі webhook вимикається |
| Курси валют | `GET /bank/currency`, кеш 5 хв, без авторизації |
| **Юридичне обмеження** | «Якщо у вас є сервіс і ви хочете централізовано приєднатися до API для надання послуг клієнтам, потрібно підключитися до **API для провайдерів послуг**… У разі виявлення експлуатації цього API в якості корпоративного, банк залишає за собою право накласти санкції на компанію». Особистий API без корпоративного доступу дозволено, лише якщо «дані клієнтів не будуть надходити на ваші сервери» |
| Корпоративний API | [заявка на авторизацію](https://api.monobank.ua/docs/corporate.html) з відкритим ключем secp256k1, підпис запитів `X-Sign`; після схвалення банком клієнт авторизується у вашому сервісі |

**Висновок:** оскільки операції мають потрапити в нашу PostgreSQL, **легальний шлях лише один — корпоративний API для провайдерів**. Спершу подати заявку, лише потім розробляти. Строки й критерії схвалення — **UNVERIFIED**.

### 6.1 Архітектура інтеграції (після схвалення)

1. Користувач авторизується через corporate flow → зберігаємо токен **зашифрованим** (AES-GCM, ключ з env або KMS), ніколи не логуємо.
2. Webhook → `POST /api/bank/mono/webhook` → **вставка як `pending`-транзакція**. Потік pending з автоочищенням через 24 год **уже існує** (REPORT.md, п.7). Для банківських операцій треба збільшити TTL або ввести окремий статус.
3. Категорія: MCC → канонічна категорія (§6.2) → словник і історія → LLM лише для неоднозначних.
4. Дедуплікація: `extra_data.bank_id` + унікальний індекс `(user_id, (extra_data->>'bank_id'))`.
5. UI: «5 нових операцій з monobank» → підтвердити все або по одній. Вручну записані дублікати (ви записали «кава 120» і прийшла банківська операція на 120) зводяться за сумою ±0 і датою ±1 день.
6. Банки monobank ↔ цілі «Копійки» (`goals`) як опційне дзеркало.
